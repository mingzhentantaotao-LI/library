## 本周关键判断

### 判断 1：现在最重要的不是扩功能，而是验证维护机制

当前项目最容易犯的错误，是在结构刚稳定一点的时候就开始做更多功能，例如：

- ingest 自动化
- review 自动化
- 搜索工具
- 更复杂的 lint
- 前端浏览层

这些都不是当前阶段最优先的。现阶段更重要的是确认：

- 现在的知识对象划分是否合理
- 单轮 ingest 规则是否能长期执行
- source page 是否足够支撑后续追溯
- review 机制应该如何定义，而不是如何实现

### 判断 2：学习材料验证价值正在下降，下一轮必须切到工作材料

目前已经连续用学习笔记做了真实 ingest，虽然对规则固化很有帮助，但继续使用学习材料，会让项目验证变得偏科。  
下一轮更应该使用：

- 项目复盘
- 工作周记
- 需求分析
- 方案草稿

因为这类材料更容易同时触发：

- project 更新
- decision 沉淀
- method 提炼
- topic 取舍

它们比学习笔记更接近未来的真实维护压力。

### 判断 3：当前最大的模糊点不是结构，而是“材料落点判断”

随着真实 ingest 增加，越来越明显的问题不是“有没有地方放”，而是“优先应该落到哪个已有页”。

例如同一份材料可能同时相关于：

- personal-knowledge-base-v1
- llm-context-engineering
- knowledge-base-maintenance
- agent-workflow-design

如果没有更明确的优先级规则，后续容易出现：

- 同类材料落点不一致
- topic 更新偏随机
- project 页承接过多杂项内容

这意味着下一阶段最值得补的不是页面类型，而是“已有页面选择优先级”的判断规则。

## 当前问题与风险

### 1. 工作材料验证不足

目前最明显的短板是：真实材料 still 偏学习输入，对工作内容的覆盖不足。  
这会导致 project page、decision page 的真实价值还没有被充分验证。

### 2. reviews 机制尚未建立

虽然已经具备定义 reviews 的条件，但现在还没有正式的 review 规则，也没有 review 输出模板。  
如果不尽快定义，后续 ingest 越多，结构漂移风险越高。

### 3. 来源字段仍然略简

source page 的最小模板已经可用，但对这类情况还不够明确：

- 无外部 URL 的工作材料
- 来自聊天整理的材料
- 来自临时手工笔记的材料
- 同一主题多份近似来源如何区分

### 4. 工具化还停留在最小阶段

虽然已经有 lint，但仍然缺少更顺手的日常操作入口，比如：

- make lint
- make review
- ingest checklist
- source page 模板片段

不过这些目前不是主要矛盾。

## 本周做出的决策

### 决策 1：V1 阶段不进入复杂自动化

在没有经过更多真实工作材料验证之前，不做 ingest 自动化，不做 review 自动化，不做复杂 RAG，不做数据库和前端。  
当前优先级仍然是“让结构和规则稳定”。

### 决策 2：下一步先定义 reviews 规则，再做下一轮工作材料 ingest

不直接进入脚本开发，而是先定义：

- review 的触发时机
- review 的检查项
- review 的输出格式
- review 是否回写 wiki

定义完规则后，再做下一轮真实工作材料 ingest，观察 rules 是否仍然成立。

### 决策 3：后续真实 ingest 必须优先使用工作材料

除非为了补充某个明确主题，否则下一轮 ingest 默认优先工作材料，不再优先学习笔记。
