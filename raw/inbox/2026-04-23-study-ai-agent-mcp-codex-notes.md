AI 这几年冒出来的一堆名词、流程，彼此到底怎么连起来。

我先给你一个总图，然后再拆开讲。

你可以把现在这套 AI 应用体系理解成：

模型 是大脑。
上下文 是它当下拿到的信息。
工具 是它能调用的外部能力。
Agent 是“会自己规划并调用工具来完成任务”的运行方式。
MCP 是把外部工具和数据，标准化接进模型的一种“通用接口协议”。
Codex 则是偏编程场景的 agent，能读代码、改文件、跑命令、接工具。OpenAI 官方文档现在明确把 MCP 说成“连接模型与工具和上下文”的协议，并说明 Codex 在 CLI 和 IDE extension 里都支持 MCP。

先讲 MCP。

MCP = Model Context Protocol。 它本质上不是模型，也不是某个具体工具，而是一个开放协议。它的作用是：让不同 AI 客户端，能用统一方式去连接外部工具和数据源，而不是每接一个系统就各写一套私有集成。Anthropic 最早公开介绍时就把它定义为一种开放标准，用来把 AI 系统和数据源做安全的双向连接；OpenAI 的 Apps SDK 文档也把它定义为“连接大模型客户端与外部工具和资源的开放规范”。

你可以把 MCP 想成 AI 世界里的“USB-C”。
不是说它本身会干活，而是说：只要双方都按这个协议说话，就能插上。

更具体一点，MCP 里通常有三类角色：

Host / Client：发起调用的一方。比如 ChatGPT、Codex、编辑器里的 agent。
MCP Server：暴露能力的一方。比如一个文档搜索服务、数据库查询服务、浏览器控制服务。
Tools / Resources：Server 提供给模型使用的具体能力或内容。OpenAI 文档里明确写到，MCP server 会暴露工具，模型可以在对话中调用；还可以返回其他资源或元数据。

所以一个简单例子是：

你问 Codex：“去查 OpenAI 文档里 Responses API 的工具参数。”
Codex 本身不是靠记忆硬答，而是通过一个 MCP server 去搜索并读取官方文档。OpenAI 官方就给了一个公开的 Docs MCP，专门提供开发文档的只读访问；他们还在 Codex 技能文章里明确写过，遇到 OpenAI API 集成工作时，Codex 可以通过 Docs MCP 查当前文档，而不是凭记忆回答。

这时候你就能看出 MCP 的价值：

以前是：
模型 + 私有 API 集成 A
模型 + 私有 API 集成 B
模型 + 私有 API 集成 C

现在变成：
模型客户端 ↔ MCP 协议 ↔ 各种 MCP servers

这会让接入外部系统更统一、更容易迁移。Anthropic 的介绍里就明确说，MCP 的目标之一就是替代碎片化集成，让 AI 获取数据更简单、更可靠。

然后说你最容易混淆的一件事：

MCP 和 function calling 不是一回事，但很像。

function calling 更像“我在自己应用里，手工定义几个函数给模型调用”。
MCP 更像“我按一个标准协议把一整类工具系统暴露给模型”。
OpenAI 的工具文档把 connectors 和 remote MCP servers 放在 function calling 之外，作为给模型扩展能力的另一种机制；它们都通过 mcp 这种工具类型接入，但连接的是外部 MCP 服务，而不是你在本地代码里随手塞进去的几个函数。

再进一步：

Connector 可以理解成 OpenAI 维护好的、面向常见服务的 MCP 包装层。
比如 Google Workspace、Dropbox 这种常见服务，OpenAI 文档就直接把 connectors 描述为“OpenAI-maintained MCP wrappers”。
而 remote MCP server 则是任何实现了远程 MCP 协议、公开可访问的服务。

这也是为什么你会看到现在很多地方都在说：

ChatGPT 可以接 connector，
Codex 可以接 MCP，
Responses API 也能直接接 remote MCP server，
Deep Research 也在探索 MCP-backed connectors。

接下来，我把 AI 名词体系给你按“从底到上”讲一遍。你以后再看到这些词，就能知道它们在什么层。

第一层，Model（模型）。
这就是大脑本体。比如 GPT-5.4、Codex 相关模型。模型擅长理解、生成、推理，但它默认不知道你的私有数据，也不能天然操作外部系统。Responses API 文档也把模型能力和外部工具能力区分开来：模型本身负责生成响应，工具负责扩展能力。

第二层，Prompt（提示词）。
就是你对模型下达的任务描述。很多人一开始以为 AI 主要就是“写 prompt”，但现在这只是最表层。因为只靠 prompt，模型能动用的信息和能力都很有限。

第三层，Context（上下文）。
就是模型当前看到的全部信息，包括你的消息、历史对话、系统指令、上传文件、检索到的资料、工具返回结果。MCP 这个名字里那个 “Context”，你就可以理解成“把本来不在模型脑子里的外部信息，以标准化方式送进来”。这一点在 MCP 官方介绍和 OpenAI Apps SDK 里都是同一个方向：把外部资源和工具接进模型运行环境。

第四层，Tool（工具）。
这是模型可调用的外部能力。比如 web search、file search、code interpreter、computer use，也包括 remote MCP servers。OpenAI 的 Responses API 现在就是把这些能力统一放进一个工具体系里。

第五层，RAG（Retrieval-Augmented Generation）。
虽然你这次没点名，但这是最常见术语之一。它的意思通常是：先检索外部资料，再把检索结果塞进上下文，让模型基于这些资料回答。你可以把它看成一种工作流，不是单独一种模型。MCP 不是等于 RAG，但 MCP server 很适合承载检索型能力；OpenAI 关于构建 MCP server 的文档，就示范了如何把私有向量库接成一个可被 ChatGPT/API 使用的远程 MCP server。

第六层，Agent（代理）。
这是很关键的概念。Agent 不是一个具体模型名，而是一种运行模式：模型不只是回答一句话，而是会自己拆任务、决定是否查资料、是否调用工具、是否继续执行下一步。OpenAI 在 2025 年开发者总结里也明确提到，随着模型在规划、工具使用和长链路任务上的提升，很多团队从“分步 prompting”转向“委托给 agents”。

第七层，Subagent（子代理）。
就是把大任务再分给多个更专门的 agent 并行处理。Codex 官方文档明确写到，它可以生成 specialized agents 并行完成代码库探索、多步骤功能实现等任务，然后把结果汇总回来。

第八层，Workflow（工作流）。
这是把模型、工具、检索、权限、测试、人工确认串起来的一套执行路径。真实可落地的 AI 项目，重点常常不在“模型多聪明”，而在工作流设计是否合理。比如“先检索，再规划，再调用工具，再生成结果，再验证”。你现在做的很多东西，本质上都应该按 workflow 思维来理解，而不是按“一个神奇 AI 一把梭”来理解。

第九层，Approval / Sandbox / Guardrails（审批、沙箱、护栏）。
这是 agent 真正落地时非常关键的一层。因为一旦模型能访问数据、运行代码、调用外部系统，就会有风险。MCP 规范本身就把安全与信任单独列为重点，强调用户同意、控制权、数据隐私；OpenAI 的 Realtime MCP 文档也写到，MCP 工具调用可以要求审批。

你如果把这些词串起来，整个现代 AI 应用流程大概是这样的：

用户提需求 → 模型理解任务 → 判断是否需要外部信息/外部动作 → 调用检索或 MCP 工具 → 工具返回结构化结果 → 模型基于结果继续推理 → 生成答案/代码/动作 → 必要时再循环几轮 → 输出最终结果。

如果是编程场景，再加两步：

改代码 → 跑测试/检查 → 再根据反馈继续修。

这也是为什么我前面一直说，Codex 的上限不只是模型能力，而是“有没有反馈闭环”。官方文档对 agent、Codex、MCP 的描述，基本都在强调这一点：工具调用、文档访问、并行子代理、审批、结果验证。

现在回到你最关心的实际理解方式：

对于你来说，MCP 不需要先从“协议细节”去学。
你应该从“它在系统里扮演什么角色”去理解。

你可以记成这句：

MCP 不是 AI 本身，而是 AI 连接外部世界的标准接口。

比如：

你要让 AI 查公司知识库，
那就需要一个知识库检索能力。
这个能力可以被封装成 MCP server。

你要让 AI 操作浏览器，
那就需要一个浏览器控制能力。
这个能力也可以被封装成 MCP server。

你要让 AI 查 Figma、Notion、数据库、订单系统、项目文档，
本质上都可以走 MCP 这条路。
OpenAI 的 Codex 页面甚至直接举例说，可以用 MCP 让 Codex 接第三方文档、浏览器、Figma 这类工具。

所以你以后看产品和方案时，可以这样分辨：

如果它说“模型回答得更聪明”，你要问：
它只是换了更强模型，还是接了外部检索和工具？

如果它说“可以连你的系统”，你要问：
它是私有 function calling、原生 API 集成，还是 MCP？

如果它说“能自动完成任务”，你要问：
它只是单轮生成，还是 agent 工作流？有没有审批、测试和回滚？

最后，我把最容易混淆的几个词，给你做一个极简对照。

LLM：大语言模型，本体大脑。
Prompt：给模型的指令。
Context：模型当前可见的信息。
Embedding / Vector Store：把文本转成便于语义检索的表示和存储方式，常用于 RAG。
RAG：先检索，再生成。
Tool use / Function calling：模型调用外部能力。
Agent：模型会自己规划并调用工具完成任务。
MCP：把外部工具和资源标准化接给模型的协议。
Connector：通常是平台维护好的 MCP 化连接器。
Codex：偏软件开发场景的 agent 产品/体验，能接代码库、终端、MCP、子代理等能力。

你如果要真正把这些吃透，最好的学习顺序不是“先背名词”，而是：

先理解 模型 和 上下文。
再理解 检索/RAG 和 工具调用。
再理解 agent。
最后再看 MCP，你就会发现它其实是 agent 时代的“基础设施层”，不是一个神秘的新模型名。这个判断和 OpenAI 现在把 MCP 放进工具、连接器、Apps SDK、Codex、Realtime 这些体系里的方式是一致的。
