# Decision 002：先做薄前端，继续文件系统优先

## 背景

2026-04-28，用户明确调整方向：当前阶段需要先完成一个相对简单的网页，用于查询、上传、删除个人知识库文件；数据库可以延后；文件管理的 AI 化接入希望同步进行。

## 决策

- 在 V1 的 Markdown 知识库之上增加一个薄 Web 层。
- Web 层优先服务文件管理：查询、上传、预览、删除。
- 数据库继续延后，不作为当前阶段的前置条件。
- 底层仍以 `raw/` 和 `wiki/` 文件系统结构作为事实来源。
- 删除默认采用“移入 `.trash/` 回收站”的安全删除，不做不可恢复的物理删除。
- AI 文件管理先以可插拔方式接入：默认提供本地规则建议，同时预留 `KB_AI_COMMAND` 外部命令钩子。

## 理由

- 现有 `raw/ + wiki/` 结构已经通过多轮 ingest 验证，可以先被网页层调用，而不是被数据库重构替换。
- 查询、上传、删除是个人知识库进入日常使用的最低交互闭环。
- 数据库会引入迁移、同步和权限边界问题，当前还不值得成为第一优先级。
- AI 文件管理需要先落在清晰动作上：分类建议、来源页草稿、关联页面建议，而不是直接自动改写知识库。

## 当前实现边界

- 当前 Web 层不做用户系统和权限系统。
- 当前 Web 层不做全文索引数据库，只做文件扫描和轻量文本匹配。
- 当前 AI 接入不直接提交 ingest 结果，只生成建议和草稿。
- 当前删除只移动到 `.trash/`，避免误删。

## 影响

- `AGENTS.md` 和 `README.md` 中关于“不做前端”的 V1 边界需要修订为：允许一个薄 Web 层，但继续延后数据库和复杂 RAG。
- 后续若需要公网访问，应单独补充认证、反向代理和备份策略。
